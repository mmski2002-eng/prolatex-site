# Про-Латекс — сайт бренда латексных матрасов

Сайт компании «Про-Латекс»: матрасы, подушки и тонкие матрасы из натурального бельгийского латекса.

Устроен из двух частей:

- **Витрина (frontend)** — Next.js 16, то, что видит посетитель. Именно она отдаёт страницы сайта.
- **Админка (wp)** — WordPress без своего внешнего вида («headless»), нужен только чтобы редактировать тексты и получать заявки. Витрина забирает у него данные по сети.

Важно: **витрина работает и без WordPress**. Если админка не запущена, сайт берёт все данные из файлов `data/*.json` и выглядит точно так же. Поэтому для локального просмотра сайта WordPress поднимать не обязательно.

Но есть обратная сторона: **пока WordPress запущен — главный он, а файлы становятся запасным вариантом**. На боевом сервере админка работает всегда, поэтому там сайт показывает данные из неё, а не из репозитория. Что это значит на практике — в разделе «Где лежат данные».

### Зачем вообще нужен WordPress

Данные о товарах лежат в файлах, и без админки сайт прекрасно живёт. WordPress держат ради двух вещей, которые файлами не закрыть:

- **Заявки с форм.** Отправленная посетителем заявка становится записью в админке: имя, телефон, модель, размер, откуда пришёл. Смотреть их в файле на сервере было бы неудобно.
- **Правки без программиста.** В админке заведены разделы «Матрасы», «Подушки», «Тонкие матрасы», «Отзывы» и блог. Задумано так, что менеджер меняет название, описание, жёсткость, высоту или порядок модели в каталоге прямо в браузере — без выкладки сайта.

Если админкой для товаров не пользуются, а всё правится через код, чтение данных из WordPress можно отключить переменной `WP_DISABLED=1` — тогда витрина будет брать товары и блог только из файлов, и правки перестанут «теряться». На приём заявок это не влияет: они по-прежнему уходят в админку.

## Быстрый старт: посмотреть сайт локально

Откройте терминал и выполните по очереди:

```bash
git clone https://github.com/mmski2002-eng/prolatex-site.git
cd prolatex-site/frontend
npm ci
npm run dev
```

Откройте в браузере **http://localhost:3000** — сайт работает.

`npm ci` скачивает библиотеки строго тех версий, что записаны в `package-lock.json`. Делается один раз; дальше достаточно `npm run dev`.

> **Про папку с проектом на Windows.** Кладите проект в короткий путь — например `C:\prolatex-site`. Если полный путь получается очень длинным (глубоко вложенные папки), сборка падает с ошибкой `Expected workStore to be initialized` — это ограничение Windows на длину пути, а не поломка проекта.

## Структура проекта

```
prolatex-site/
├── data/                  — данные сайта: модели матрасов, подушки,
│                            тонкие матрасы, тексты страниц (JSON-файлы)
├── frontend/              — витрина на Next.js
│   ├── src/app/           — страницы сайта (папка = адрес страницы)
│   ├── src/components/    — повторно используемые блоки (шапка, подвал,
│   │                        карточки, галерея, формы)
│   ├── src/data/          — копия data/*.json, из неё читает витрина
│   ├── src/lib/           — работа с данными, SEO-разметка, утилиты
│   └── public/            — картинки, видео, логотипы, шрифты
├── wp/                    — WordPress-админка
│   ├── plugins/prolatex-core/  — свой плагин: типы записей, REST API,
│   │                             приём заявок, импорт данных
│   └── .wp-env.json       — настройки локального WordPress
└── BRIEF.md               — техническое задание и правила проекта
```

### Где лежат данные

Данные сайта (модели, цены, фотографии, размеры) хранятся **в трёх местах**:

| Где | Зачем |
|---|---|
| `data/*.json` | исходник в репозитории |
| `frontend/src/data/*.json` | копия, из которой витрина читает, когда WordPress недоступен |
| `/var/www/prolatex-wp/wp-content/prolatex-data/*.json` на сервере | то, что реально показывает боевой сайт |

Первые два файла должны совпадать: правите модели вручную — правьте оба, иначе локальный просмотр покажет одно, а импорт в админку положит другое.

**Третье место — главная причина, по которой правки «не появляются» на сайте.** Боевой WordPress читает свою папку `prolatex-data`, и она живёт отдельно от репозитория. Пока туда не положить новый файл, сайт будет показывать старые цены и фотографии, сколько сборку ни выкладывай.

Поэтому правило простое:

- поменяли **вёрстку или тексты в коде страницы** — достаточно пересобрать и выложить витрину;
- поменяли **данные** (цены, фото, размеры, состав моделей) — нужно ещё положить те же JSON-файлы в папку WordPress на сервере и сбросить его кеш, см. «Обновление данных на сервере».

## Настройки через переменные окружения

Все необязательные — без них сайт работает на локальных данных.

| Переменная | Смысл | По умолчанию |
|---|---|---|
| `WP_API_URL` | адрес REST API WordPress | `http://localhost:8890/wp-json` |
| `WP_DISABLED` | `1` — не читать из WordPress товары и блог, брать их только из локальных JSON. На отправку заявок не влияет | не задана |
| `PARTNER_SECRET` | общий секрет с WordPress для обновления кэша страниц | значение для разработки |

Если WordPress не отвечает за 1,2 секунды, витрина молча переключается на `data/*.json` — сайт не ломается.

Заявки с форм уходят в WordPress. Если он недоступен, заявка сохраняется в файл `frontend/leads-fallback.json`, чтобы не потерялась. Этот файл намеренно не хранится в репозитории.

## Локальная админка WordPress (по желанию)

Нужна, только если хотите редактировать содержимое через привычную панель WordPress.

```bash
cd wp
npx @wordpress/env start
```

Поднимется WordPress на **http://localhost:8890** (тестовый — на 8891). Сам WordPress скачивается автоматически, в репозитории его нет.

Импорт данных из `data/*.json` в базу:

```bash
npx @wordpress/env run cli wp prolatex import
```

Импорт можно запускать повторно — записи сопоставляются по короткому имени (slug) и не задваиваются.

Плагин `prolatex-core` добавляет: типы записей для матрасов и статей, REST API для витрины, приём заявок и команду импорта.

## Что нужно доделать в админке

Два момента, о которых важно знать заранее.

### 1. Латинские адреса страниц — нужен отдельный плагин

Когда статью в блоге называют по-русски, WordPress по умолчанию делает адрес страницы из русских букв, и в браузере он превращается в нечитаемую строку вида `%D0%BC%D0%B0%D1%82%D1%80%D0%B0%D1%81`. Для поисковиков и для ссылок это плохо.

**В админку нужно поставить плагин транслитерации** — например, Cyr-To-Lat. Он автоматически переводит русские названия в латиницу: «Как выбрать матрас» → `kak-vybrat-matras`.

Свой плагин `prolatex-core` умеет делать это сам, но **только для статей блога** (тип записей `article`). На остальное — обычные страницы, рубрики, метки, названия загруженных файлов — это не распространяется, поэтому отдельный плагин всё равно нужен.

### 2. Уведомления о заявках на почту не работают

В коде отправка письма есть: когда с сайта приходит заявка, плагин пытается отправить её на почту получателя (адрес задаётся в настройках админки, по умолчанию берётся почта администратора WordPress).

**Но фактически письма не уходят — у проекта пока нет своего домена.** Сайт живёт по IP-адресу, почтового ящика на домене нет, отправка через сторонний почтовый сервер (SMTP) не настроена. Письма с такого сервера почтовые службы либо не примут, либо отправят в спам.

Что при этом происходит с заявками: **они не теряются**. Каждая сохраняется в админке WordPress как отдельная запись — со всеми полями: имя, телефон, почта, товар, размер, сообщение, время. Смотреть их нужно вручную в панели администратора.

Чтобы включить уведомления, понадобится: купить домен, привязать его к сайту, завести почтовый ящик и настроить отправку через SMTP (обычно ставят плагин вроде WP Mail SMTP), после чего указать адрес получателя в настройках заявок.

## Как устроен рабочий («боевой») сервер

Сайт развёрнут на сервере `95.215.108.99`:

| Что | Где |
|---|---|
| Файлы сайта | `/var/www/prolatex-next` |
| Служба запуска | systemd, `prolatex-next.service` |
| Внутренний порт витрины | 3050 (только внутри сервера) |
| nginx отдаёт наружу | порт **8083** → http://95.215.108.99:8083/ |
| WordPress-админка | порт **8084** → http://95.215.108.99:8084/wp-admin/ |

**Порты менять нельзя** — на них настроен nginx.

Git-репозитория на сервере нет: туда заливается уже собранная версия сайта.

### Порядок обновления сайта

1. Собрать локально:

   ```bash
   cd frontend
   npm run build
   ```

   Настройка `output: "standalone"` в `next.config.ts` делает самодостаточную сборку — на сервере не нужно ставить библиотеки.

2. Сделать резервную копию текущей версии на сервере:

   ```bash
   ssh root@95.215.108.99 "cd /var/www/prolatex-next && cp -a .next .next.bak-$(date +%Y%m%d-%H%M%S)"
   ```

3. Залить новую сборку во временную папку (чтобы сайт не лежал во время загрузки):

   ```bash
   scp -r .next/standalone/.next/* root@95.215.108.99:/var/www/prolatex-next/.next.new/
   scp -r .next/static           root@95.215.108.99:/var/www/prolatex-next/.next.new/
   scp    .next/standalone/server.js root@95.215.108.99:/var/www/prolatex-next/server.js
   ```

   Новые картинки из `public/` заливаются отдельно, в соответствующую папку внутри `/var/www/prolatex-next/public/`.

4. Переключить и перезапустить:

   ```bash
   ssh root@95.215.108.99 "cd /var/www/prolatex-next && \
     chown -R www-data:www-data .next.new server.js && \
     rm -rf .next.old && mv .next .next.old && mv .next.new .next && \
     systemctl restart prolatex-next && systemctl is-active prolatex-next"
   ```

5. Проверить сайт: http://95.215.108.99:8083/

Если что-то сломалось — вернуть предыдущую версию:

```bash
ssh root@95.215.108.99 "cd /var/www/prolatex-next && rm -rf .next && mv .next.old .next && systemctl restart prolatex-next"
```

### Обновление данных на сервере

Нужно **только когда менялись** `data/*.json`: цены, фотографии моделей, размеры, состав. Если правился код страниц — этот раздел пропускаем.

1. Залить обновлённые файлы, сделав резервную копию прежних:

   ```bash
   scp data/mattresses.json data/toppers.json data/pillows.json data/content.json root@95.215.108.99:/tmp/

   ssh root@95.215.108.99 'D=/var/www/prolatex-wp/wp-content/prolatex-data; \
     TS=$(date +%Y%m%d-%H%M%S); \
     for f in mattresses.json toppers.json pillows.json content.json; do \
       cp -a $D/$f $D/$f.bak-$TS; \
       cp /tmp/$f $D/$f; \
     done; \
     chown www-data:www-data $D/*.json; chmod 644 $D/*.json'
   ```

   Заливать можно только те файлы, которые менялись.

2. Сбросить кеш админки — иначе она ещё пять минут будет отдавать старое:

   ```bash
   ssh root@95.215.108.99 'cd /var/www/prolatex-wp && \
     for r in mattresses toppers pillows content; do \
       sudo -u www-data wp transient delete prolatex_data_$r --allow-root; \
     done'
   ```

3. Перезапустить витрину, чтобы она перечитала данные:

   ```bash
   ssh root@95.215.108.99 "systemctl restart prolatex-next"
   ```

4. Проверить, что админка отдаёт новые данные:

   ```bash
   curl -s http://95.215.108.99:8084/wp-json/prolatex/v1/toppers
   ```

   Страницы сайта обновляются не мгновенно: витрина держит готовые страницы до пяти минут. Если сразу после перезапуска видно старое — подождите минуту и обновите страницу.

## Пароли и доступы

В репозитории их нет и быть не должно. Логины, пароли и адреса админки хранятся в файле `СЕКРЕТЫ.md` — он лежит **на уровень выше** папки проекта и в Git не попадает.

В репозиторий можно класть только публичное: ссылки на сайт, названия разделов, адреса каналов.

## Если что-то не работает

| Симптом | Причина и что делать |
|---|---|
| `Expected workStore to be initialized` при сборке | слишком длинный путь к папке проекта в Windows — перенесите проект ближе к корню диска, например в `C:\prolatex-site` |
| Порт 3000 занят | запустите на другом порту: `npm run dev -- -p 3001` |
| Локальный сайт показывает старые данные | правки внесены только в `data/`, а витрина читает `frontend/src/data/` — синхронизируйте файлы |
| **Боевой** сайт показывает старые цены или фото после выкладки | данные не залиты в папку WordPress на сервере — см. «Обновление данных на сервере». Самая частая причина |
| После `git clone` не запускается | не выполнен `npm ci` в папке `frontend` |
| Заявки с форм не приходят | не запущен WordPress; заявки сохраняются в `frontend/leads-fallback.json` |
| Письма о заявках не приходят на почту | так и задумано на сегодня — нет домена и SMTP, см. «Что нужно доделать в админке»; заявки смотрите в админке WordPress |
| В адресе статьи блога русские буквы или `%D0%BC%D0%B0…` | не установлен плагин транслитерации в админке, см. «Что нужно доделать в админке» |
